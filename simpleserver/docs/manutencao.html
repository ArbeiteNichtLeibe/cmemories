🎯 Filosofia do Projeto

"Funciona ou Quebra"

O sistema não tolera inicializações parciais. Se qualquer componente crítico falhar, o processo inteiro é encerrado. Isso garante que nunca haja um estado inconsistente ou "meio funcionando". Cada módulo deve ser autocontido e verificar suas dependências na inicialização.

  • Zero heap padrão – toda memória é alocada na MemoryManagerThread (arena).
  • Zero exceções – funções retornam bool e populam char* outError.
  • Não há fallbacks – se uma configuração obrigatória falta, o sistema para.
  • RAII customizado – para arquivos e locks, mas memória é gerenciada via arena.

🔐 Autenticação e Token

Token derivado do TPM

O servidor HTTP exige autenticação obrigatória via Authorization: Bearer <token>. O token é gerado a partir do pepper (64 bytes obtidos do TPM) combinado com um salt fixo, e submetido a SHA‑256, resultando em uma string de 64 caracteres hexadecimais.

  • Arquivo de persistência: /home/memorandos/webserver.conf
  • Geração automática: se o arquivo não existir ou o token for inválido, o servidor gera um novo.
  • Vínculo ao hardware: portar o executável para outra máquina força a regeneração do token.
Salt atual: "Onegai, bite, please" (definido em auth.cpp).

⚠️ Ponto Crítico

O HttpServer::initialize não tem fallback para http_docs. Se a chave não existir no arquivo de configuração, ele retorna false e o sistema inteiro falha. Isso é proposital – ou a configuração está correta, ou o sistema não roda.

🧩 Como Adicionar uma Nova Rota

Passo a passo
  1. Abra simpleserver/src/router.cpp.
  2. Localize a função route_request.
  3. Adicione um novo bloco if antes do return true; final.
  4. Use o padrão:
if (strcmp(req->method, "GET") == 0 && strcmp(req->path, "/minha-rota") == 0) {
    resp->status_code = 200;
    resp->content_type = "application/json";
    resp->body = "{\"mensagem\":\"Olá, mundo!\"}";
    resp->body_len = strlen(resp->body);
    return true;
}

Importante: a resposta não deve usar alocação dinâmica (heap) – use strings literais ou buffers estáticos. Para respostas dinâmicas, aloque um buffer na arena via MemoryManagerThread::allocate() e preencha-o.

Exemplo real: A rota /api/query gera um ticket e inicia processamento assíncrono – veja o código para referência.

🧹 Como Adicionar um Novo Middleware

Exemplo: Logging ou Rate Limiting

O servidor HTTP processa cada requisição na função HttpServer::process_request (em http_server.cpp). Para adicionar um middleware (ex.: logging, rate limiting), insira o código após a autenticação e antes do roteamento. 

// ----- MIDDLEWARE EXEMPLO (logging) -----
fprintf(stdout, "📝 %s %s from %s\n", method, path, client_ip);
// ----------------------------------------

Se o middleware precisar de estado (ex.: contador de requisições), use um std::atomic ou um mutex, e aloque estruturas na arena se forem grandes.

🧠 Decisões Técnicas Importantes

1. Bitmap do BlockAllocator na Stack

O BlockAllocator mantém um bitmap de 4 KB na stack (não na arena). Isso foi uma exceção controlada aprovada pela equipe, pois o bitmap tem tamanho fixo e pequeno, e colocar na stack libera toda a região mmap para dados. Veja a nota em block_allocator.cpp.

2. Uso de std::string_view e Buffers da Arena

Embora o projeto proíba alocação dinâmica no heap, usamos std::string_view (que é apenas uma referência) para manipular partes do buffer da requisição. Todos os buffers de dados (cabeçalhos, corpos) são alocados via MemoryManagerThread::allocate().

3. Tokens de Autenticação e TPM

O token é derivado do pepper do TPM para garantir que a autenticação esteja vinculada ao hardware. A persistência em /home/memorandos/webserver.conf permite que o token sobreviva a reinícios. Se o arquivo for apagado ou corrompido, o servidor gera um novo token automaticamente.

📋 Configuração Essencial

O arquivo /etc/memorandos/config.conf deve conter pelo menos:

workeruser = andre
http_port = 9010
http_ip = 127.0.0.1
http_docs = /home/memorandos/www

Nota: O HttpServer não aceita fallback para http_docs – a chave deve existir e apontar para um diretório válido, caso contrário o sistema para.

🔌 Integração com o ShutdownManager

Ordem de Desligamento
  1. HttpServer::shutdown() – para de aceitar conexões e aguarda workers
  2. JSONWorker::JsonGenerator::destroyInstance()
  3. TPMStart::shutdownTPM()
  4. FakeRedis::finalize()
  5. LerConfig::Config::setMemoryManager(nullptr)
  6. MemoryManagerThread::shutdown()

Essa ordem garante que nenhum componente tente usar recursos já liberados.

📌 Resumo das Boas Práticas

  • Sempre use Utils::safeCopyString para copiar strings com segurança.
  • Nunca aloque no heap – use mm->allocate() e libere com mm->free().
  • Nunca use std::string ou std::vector em produção – use char[] com tamanho fixo ou buffers da arena.
  • Funções que podem falhar devem retornar bool e preencher um buffer de erro.
  • Inicialização é crítica – se algo falhar, retorne false para que o sistema pare.
  • Não use #pragma once em arquivos .cpp – apenas em cabeçalhos.
  • Não use forward declarations – inclua os headers completos.
