📘 Guia do Desenvolvedor – Memorandos

Documentação técnica para manutenção e extensão do sistema de servidor web com autenticação TPM, processamento assíncrono de JSON e gerenciamento zero‑heap.

v1.0 ESTÁVEL 📅 2026-08-21

🧩 Estrutura Geral do Projeto

O sistema é modular e segue o princípio de injeção de dependência. Os principais componentes são:

  • MemoryManagerThread – gerenciador de arena (zero‑heap). Aloca regiões de memória mmap e controla empréstimos por thread.
  • FakeRedis – armazenamento chave‑valor em memória (usando a mesma arena).
  • TPMManager – interage com o TPM 2.0 para obter um pepper (64 bytes) e derivar chaves.
  • JsonGenerator – compõe JSON a partir de templates com substituição de placeholders.
  • JsonWorker – processa requisições assíncronas (cada chamada gera um ticket no Redis e um worker processa em segundo plano).
  • HttpServer – servidor HTTP com dois workers, autenticação obrigatória por Bearer Token, parsing de cookies e roteamento.
  • LerConfig – leitor de configurações do arquivo /etc/memorandos/config.conf, com alocação na arena.

O fluxo de inicialização é orquestrado pelo main.cpp e pelo módulo JSONStart, que centraliza a inicialização dos serviços críticos.

🚀 Fluxo de Inicialização

Ordem de execução no main.cpp
  1. Verifica privilégios de root e processa argumentos.
  2. Cria diretório de configuração /etc/memorandos e arquivo config.conf se não existir.
  3. Lê workeruser do config e ajusta permissões do diretório /home/memorandos.
  4. Drop de privilégios para o usuário workeruser.
  5. Inicializa MemoryManagerThread com a quantidade de GB solicitada.
  6. Injeta o MemoryManager no LerConfig.
  7. Carrega as configurações do arquivo config.conf.
  8. Inicializa FakeRedis.
  9. Inicializa TPMManager (se a flag --accepttp2mchanges=yes for fornecida).
  10. Chama JSONStart::init(), que por sua vez:
    • Inicializa JsonGenerator (aloca 256 MB na arena).
    • Adiciona templates padrão (ex: usuario_teste).
    • Executa um teste de processamento de requisição (opcional).
    • Inicializa o HttpServer (passando o MemoryManager, Redis, TPMManager e um token base).
  11. Entra no loop principal aguardando sinal de interrupção.

⚠️ Importante: Se qualquer etapa crítica falhar (incluindo o HttpServer), o sistema aborta imediatamente – filosofia “funciona ou quebra”.

🔐 Autenticação e Token

🔑 Geração do Token Bearer
  • O servidor usa o pepper (64 bytes) obtido do TPM 2.0.
  • Combina o pepper com um salt fixo ("Onegai, bite, please") e calcula SHA‑256.
  • O resultado (32 bytes) é convertido para 64 caracteres hexadecimais.
  • O token é persistido em /home/memorandos/webserver.conf (com permissões 0600).
  • Na primeira execução, o token é gerado e salvo. Nas próximas, ele é lido do arquivo.
  • Todo acesso ao servidor HTTP exige o token no cabeçalho Authorization: Bearer <token>.
  • Se o token for inválido ou ausente, o servidor retorna 401 Unauthorized.

🔒 Vinculado ao hardware – O token é único por TPM. Se o programa for executado em outra máquina, um novo token será gerado, invalidando os anteriores.

🧠 Arquitetura do Servidor HTTP

Componentes do HttpServer
  • Thread de aceitação – escuta o socket, aloca um buffer de 1 MB (na arena) para os cabeçalhos e enfileira a tarefa.
  • Workers (2) – consomem a fila de tarefas, processam a requisição (autenticação, cookies, roteamento) e enviam a resposta.
  • Roteamento – feito pelo módulo router.cpp, que recebe um RequestInfo e preenche um Response.
  • Autenticação – extrai o token do cabeçalho e chama auth::verify_token().
  • Cookies – parse do cabeçalho Cookie usando cookie::parse_cookies().
  • Processamento assíncrono – a rota /api/query gera um ticket no Redis, enfileira a tarefa para o JsonWorker (que roda em background) e retorna o ticket para o cliente. O cliente pode consultar o resultado via /api/result/{ticket}.

📝 Como Adicionar uma Nova Rota

✏️ Modificando o router.cpp

No arquivo simpleserver/src/router.cpp, localize a função route_request e insira um novo bloco if com sua rota. Exemplo:

if (strcmp(req->method, "GET") == 0 && strcmp(req->path, "/minha-rota") == 0) {
    resp->status_code = 200;
    resp->content_type = "application/json";
    resp->body = "{\"mensagem\":\"Olá, mundo!\"}";
    resp->body_len = strlen(resp->body);
    return true;
}

Para rotas com parâmetros dinâmicos (ex: /usuario/{id}), use strncmp para comparar o prefixo:

if (strcmp(req->method, "GET") == 0 && strncmp(req->path, "/usuario/", 9) == 0) {
    const char* id = req->path + 9;  // extrai o ID
    // ... lógica
}

⚠️ Limites de memória – Todos os buffers para resposta devem ser alocados na arena (mm->allocate(...)) ou podem ser estáticos (const char*). Evite usar std::string ou new.

Após alterar, recompile o módulo simpleserver e o generico.

⚙️ Processamento Assíncrono de JSON

🔄 Fluxo de uma consulta
  1. O cliente envia POST /api/query com JSON contendo {"usuario": "...", "dados": "..."}.
  2. O HttpServer gera um ticket (ID único) e grava a requisição no Redis com TTL de 60s.
  3. O ticket é colocado em uma fila interna do JsonWorker (thread em background).
  4. O worker lê a requisição do Redis, aplica o template (usando JsonGenerator) e grava o resultado no Redis com TTL de 3 minutos.
  5. O cliente pode consultar /api/result/{ticket} periodicamente até receber o status "pronto".

Os templates são definidos via JsonGenerator::addTemplate() e podem conter placeholders <campo>.

🧪 Compilação e Flags

🛠️ Ambiente de desenvolvimento
  • SO: Debian 13 (Trixie), processador AMD Ryzen 7, 48 GB RAM.
  • Compilador: GCC 14.2+ (C++23).
  • Flags obrigatórias: -std=c++23 -Wall -Wextra -Wpedantic -O3 -march=native -pthread -fPIC -MMD -MP.
  • Bibliotecas: OpenSSL (para SHA‑256 e HMAC), pthread, TSS2 (para TPM).

Para compilar o sistema completo, execute make dentro dos diretórios memorymanager, fakeredis, tpm2, jsonhandler, lerconfig, uteis, simpleserver e generico (nessa ordem). O Makefile principal do generico chama os submódulos automaticamente.

📜 Regras de Codificação (Resumo)

⚠️ Normas do projeto
  • Zero‑heap / Zero‑stack – toda alocação de memória deve ser feita via MemoryManagerThread. Uso de std::string, std::vector, new, malloc é proibido, exceto em casos excepcionais e devidamente justificados (ex: stack para buffers pequenos e temporários).
  • Sem forward declarations – inclua os headers completos onde necessário.
  • Sem exceções – use bool + parâmetro de erro (char* outError, size_t errSize).
  • RAII customizado – use FileGuard e similares para recursos, mas para memória adapte ao MemoryManager.
  • Nomenclatura em inglês – variáveis, funções, classes em inglês (padrão americano).
  • Sem #pragma once em arquivos .cpp – apenas nos .hpp.
  • Thread‑safe – use std::atomic, mutex e condition_variable.

Essas regras estão documentadas em repassarsemprenoinicio.md no diretório do projeto.

🔍 Depuração e Logs

📋 Como ver o que está acontecendo
  • O HttpServer imprime no stdout as configurações lidas (porta, IP, docs).
  • O LerConfig exibe quantas chaves foram carregadas.
  • O TPM mostra os primeiros bytes do pepper e o resultado do teste de derivação.
  • O JSONStart exibe o progresso da inicialização e o resultado do teste.
  • Em caso de erro, a mensagem é copiada para o buffer de erro e o sistema aborta (exceto no teste, que é opcional).

Se precisar de mais detalhes, adicione fprintf(stdout, "...") nos pontos desejados (lembre‑se de remover após a depuração).

🧹 Shutdown

🛑 Ordem de desligamento
  1. HttpServer::shutdown() – interrompe a aceitação, aguarda os workers finalizarem e libera buffers.
  2. JSONWorker::JsonGenerator::destroyInstance() – libera recursos do gerador de JSON.
  3. TPMStart::shutdownTPM() – encerra a sessão do TPM.
  4. FakeRedis::finalize() – libera a área de dados do Redis.
  5. LerConfig::Config::setMemoryManager(nullptr) – remove a referência ao MemoryManager.
  6. MemoryManagerThread::shutdown() – libera a região mmap e finaliza as threads internas.

O desligamento é acionado pelo sinal SIGINT/SIGTERM e orquestrado pelo ShutdownManager.
